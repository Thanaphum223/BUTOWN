# Administrator account deletion

The user requests an account-delete action for TownTrack administrators. Add it to each row in บัญชีผู้ใช้ with a confirmation naming the account. A deletion removes the account from active administration lists and prevents access to TownTrack. It does not delete the central Gov account, complaints, evidence, votes, work assignments, or audit history.

Use a deleted_at timestamp with enabled=false, enforced together by a database constraint. On a later verified Gov sign-in, replace the identity binding with a new local UUID. Never restore the archived UUID, role, department, credentials, complaint ownership, votes, follows, assignments or notifications. Refresh Gov profile/residence data only from that new verified response. A disabled account without deleted_at remains blocked; deletion and suspension are intentionally different. Serialize both repeated sign-in and deletion against the existing local account to avoid restoring a deleted identity during a race. Reuse session revocation. The endpoint is administrator-only, CSRF protected and municipality scoped. Reject self-deletion. Serialize deletes per municipality and recheck the acting administrator after acquiring the lock so two administrators cannot delete each other concurrently. Return success for a repeat delete without duplicating audit records. Existing role/enable edits must reject deleted targets.

The UI shows the account name/username, explains the effect and retained records, defaults focus to cancel, prevents duplicate writes and retains a failed confirmation for retry. No real account will be deleted during testing. Use a disposable isolated test database and fictional browser fixtures.

Physical deletion would break historical references; merely disabling the account would not remove it from account lists and could be reversed accidentally by the enable switch. An explicit archived timestamp preserves history and prevents accidental reactivation. These are implementation choices under the user's standing request to finish autonomously.

Existing work remains assigned to its original account. Administrators can manage that work; no unrequested reassignment occurs.

## User correction: fresh account after deletion
The user explicitly requires deleted people to be able to join again as a new account with no former personal history. Existing non-deleted account roles remain authoritative pending clarification of the role source; never infer municipal authority from the current MEMBER membership example. This supersedes the initial permanent sign-in block.

## Initial role from Gov (subsequent user clarification)
For new identities, including a fresh identity after deletion, read the role for the TownTrack E-Service from the verified backend response, not the global system role or municipal membership role. A later local administrator edit wins on all future logins. Add editable Gov-code → TownTrack-role + department mappings in administration. Defaults recognize CITIZEN/USER/MEMBER, OFFICER, LEADER, FIELD, APPROVER, ADMIN. Never grant an unknown role implicitly. LEADER/FIELD require a configured local department.

Gov publishes serviceAccess under each active municipality membership, but its example has no non-empty serviceAccess schema. Support explicit service.code/eService.code/serviceCode and role.code/roleCode/string role representations, validating contradictory values. Match the configured E_SERVICE_CODE or an explicitly configured Gov service ID. Staff grants require an administrator-configured Gov municipality ID matching the membership; this avoids importing another municipality's authority into the single local tenant. Do not guess that binding from the first user. Missing staff scope/role/department setup returns an actionable failure and creates no account; ordinary users with no TownTrack role start as CITIZEN. Keep all integration tests synthetic; no real Gov registration, role edits or account deletion.
