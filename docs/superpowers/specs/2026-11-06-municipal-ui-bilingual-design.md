# TownTrack: municipal UI wording, bilingual screens, and UAT simulation

Date: 2026-11-06
Status: implementation design based on the user's request and confirmed clarifications; builder check: nothing important left.

## เป้าหมายและข้อตกลงที่ยืนยันแล้ว

ปรับ UI ทั้ง 6 งานตามข้อความที่ผู้ใช้แนบ ให้สอดคล้องกับการทำงานที่กำหนดและเอกสาร GOV.zip โดยคงธีมเขียวและการเชื่อมต่อจริง ผู้ใช้ยืนยันเพิ่มไทย/อังกฤษครบทุกหน้า แสดงวันนัดหมายเดิมในหน้าหัวหน้า และใช้ข้อความตัวตนที่ตรงกับ Gov Center (LINE หรืออีเมล) เหตุผลสำเร็จรูปเป็นตัวอย่างที่ต้องตรวจทาน สวิตช์จำลองอยู่เฉพาะโหมด UAT และมีป้ายจำลอง

ไม่เปลี่ยน schema, migration, API path/request/response contract, state transition หรือ role key เดิม CITIZEN/OFFICER/LEADER/FIELD/APPROVER รวมถึง ADMIN ที่มีอยู่แล้ว ไม่สร้างบัญชีหรือส่งคำร้อง/อนุมัติจริงเพื่อทดสอบ ไม่เพิ่มระบบเส้นทางกลับมา ไม่แปลข้อมูลที่ผู้ใช้กรอกหรือเปลี่ยนค่าที่ส่งเข้า API

## Approaches

1. ใช้ชุดคำแปลกลางที่มี type checking และ React subscription เปลี่ยนเฉพาะข้อความ/locale โดยคง component และ form instance เดิม เป็นแนวทางที่เสนอให้ใช้บน React/Ant Design เดิม ตรงกับขอบเขตทุกหน้าและรักษาร่างได้
2. ใช้การแทนข้อความ DOM หรือแปลหน้าอัตโนมัติ: ไม่เลือก เพราะแยกข้อความระบบจากข้อมูลผู้ใช้ไม่ได้และเสี่ยงแก้ค่าฟอร์ม
3. แปลเฉพาะหน้าที่แตะในคำขอ: ผู้ใช้เลือกให้ขยายเป็นทุกหน้าแล้ว จึงไม่ใช้วิธีนี้

แผนข้างล่างเป็นรายละเอียดของแนวทางที่ 1 การเลือกชื่อโมดูลและการแบ่งไฟล์เป็นข้อเสนอของผู้พัฒนา

## 1. ภาษาและการรักษาร่าง ครบทุกหน้า

เพิ่ม language store และ typed dictionaries ไทย/อังกฤษ ไม่เพิ่มบริการแปลภายนอกหรือส่งข้อมูลผู้ใช้ไปแปล เก็บเฉพาะภาษา th/en ใน localStorage พร้อม fallback เมื่อ storage ใช้ไม่ได้ ตั้ง document.lang และ Ant Design locale ตามภาษา ปุ่มสลับภาษามีทั้งหน้าล็อกอินและส่วนหัวหลังล็อกอิน จำภาษาเมื่อ refresh/logout/login

ขอบเขตครอบคลุม auth/registration/callback, privacy, citizen home/report/tracking/detail/following/notifications/emergency, staff queue/history/detail/resource/assignment/report/approval, teams, admin users/departments/category forms/SLA/workflow/Gov mapping/account deletion และ file upload/PDF/error/loading/empty states ชื่อบทบาท สถานะ action และคิวที่ระบบส่งมาเป็นรหัสใช้คำแปลฝั่ง UI วันที่ใช้ Asia/Bangkok และ locale ของภาษาที่เลือก

ข้อความผู้ใช้ ชื่อคน กองที่ตั้งเอง รายละเอียดเรื่อง เหตุผลที่บันทึกไว้ ชื่อไฟล์ และค่าแบบฟอร์มเป็นข้อมูลต้นฉบับ ไม่แปลหรือเขียนทับ ชื่อหมวดหมู่ทุกชื่อจาก API เป็นข้อมูลที่ผู้ดูแลเปลี่ยนได้ จึงใช้ชื่อต้นฉบับทั้งสองภาษา เพราะ contract ไม่มีตัวระบุว่าเป็นหมวดมาตรฐาน แปลเฉพาะ label และคำแนะนำของ UI ข้อผิดพลาดระบบที่รู้จักแปลด้วยข้อความที่จับคู่ไว้ ไม่ตีความข้อความอิสระเป็นคำสั่ง

การเปลี่ยนภาษาต้องไม่ใช้ key ใหม่ ไม่ reload ไม่ reset form ไม่เปิด modal ใหม่ และไม่ใช้ effect ที่โหลดค่าเริ่มต้นทับร่าง ต้องคงข้อความที่พิมพ์ พิกัด รายการทรัพยากร ไฟล์ที่เลือก/อัปโหลด และข้อมูล IndexedDB เดิม ร่างยังแยกตามบัญชี/คำร้องเดิม ภาษาทำหน้าที่แสดงผลเท่านั้น

## 2. การมอบหมายและการ์ดผู้ลงพื้นที่

Route Planning ถูกถอดออกจาก baseline แล้ว ตรวจไม่ให้มีเมนู รอบงาน การจัดหลายจุด การเรียงเส้นทางอัตโนมัติ หรือ polyline หลงเหลือ การค้นหา/เรียงตามวันที่หรือโหวตเป็นตัวกรองทั่วไป ยังใช้ได้

หน้าหัวหน้าแสดงเรื่องเดียว หมุดเดียว รายละเอียด ความเร่งด่วน วันนัดหมายเดิมแบบอ่านอย่างเดียว และแบบเลือกทีม/ผู้ลงพื้นที่ตามสิทธิ์เดิม วันนัดหมายยังมาจากเจ้าหน้าที่ส่วนกลางตามที่ผู้ใช้ยืนยัน ห้ามเพิ่มช่องเลือกวันที่ซึ่ง API ไม่ได้บันทึก

รายการ FIELD เป็น Ant Design Cards: เลขเรื่อง หัวข้อ ประเภท สถานที่ วันนัดหมาย สถานะ และจำนวนโหวต (รวม 0) มีปุ่มดูรายละเอียดและเปิดตำแหน่งเรื่องนั้น ใช้ GET detail เดิมเพื่ออ่านวันนัดหมาย/พิกัดที่ list API ไม่ส่งมา พร้อม cache ตาม id/version จำกัดงานโหลดและยกเลิกเมื่อเปลี่ยนหน้า/บัญชี ห้ามเปลี่ยน list contract หรือแสดงค่าที่เดาเอง หากโหลดไม่ได้ให้เห็นข้อผิดพลาดและลองใหม่

เปิดแผนที่เฉพาะการ์ดที่ผู้ใช้เลือกครั้งละหนึ่งแผนที่ ใช้ LocationMap/Mapbox และ fallback เดิม แสดงหมุดจุดเดียวเพื่อประหยัดหน่วยความจำมือถือ ไม่คำนวณรอบหลายงาน ไม่เรียก OSRM

## 3. ลำดับการปฏิบัติงาน FIELD

ใช้ action key และปุ่มที่ backend อนุญาตอยู่แล้ว:
- ACCEPT: ปุ่ม “กดรับงานและลงพื้นที่สำรวจ”; ไม่บังคับเหตุผล
- DECLINE: “กดปฏิเสธงาน”; เหตุผลยังบังคับ และยังส่งงานกลับหัวหน้าตาม transition เดิม ไม่ยุติเรื่องประชาชน
- หลังรับงาน เมื่อเริ่มงานหรือขอทรัพยากรได้ แสดง info:
  “ขั้นตอนปฏิบัติงาน: เมื่อสำรวจหน้างานจริงแล้ว หากวัสดุ/อุปกรณ์ปกติเพียงพอให้กด 'เริ่มปฏิบัติงานซ่อมแซม' หากเกินขีดความสามารถให้กด 'ส่งประเมินขอใช้ทรัพยากร/งบประมาณเพิ่ม'”
- REQUEST_RESOURCE: “ส่งเอกสารประเมินทรัพยากร/ของบจากหน้างาน”
- START: “เริ่มปฏิบัติงานซ่อมแซม (ใช้วัสดุ/อุปกรณ์ปกติ)”; ไม่บังคับเหตุผล
- ช่วง RESOURCE_DRAFT / RESOURCE_CHECK / RESOURCE_APPROVAL และ RESOURCE_REVISION ที่ยังรอผล: “ระงับการใช้ทรัพยากรที่ขอชั่วคราว (รอผลการพิจารณาอนุมัติ)” ไม่มีป้ายนี้หลังอนุมัติแล้ว
- แยกคำบนปุ่มออกจากคำในประวัติ ไม่ทำให้รายการอดีตกลายเป็นคำสั่ง “กด...”

## 4. ผู้มีอำนาจและผลไม่อนุมัติ

APPROVE ยังคงการทำงานเดิม ปุ่ม “อนุมัติ”
DENY ใช้ข้อความ:
“ไม่อนุมัติงบประมาณเฉพาะกิจ (ยุติใบงานซ่อมด่วนเพื่อนำเข้าแผนฯ / ประสานหน่วยงานภายนอก)”

เหนือช่องเหตุผลบังคับ แสดง Tag/Button ที่ใช้คีย์บอร์ดได้เพื่อเลือกเติมเหตุผล และผู้ใช้แก้ไขได้ก่อนยืนยัน:
1. “เกินวงเงินซ่อมบำรุงปกติ เห็นควรยุติใบงานเฉพาะกิจนี้เพื่อบรรจุเข้าแผนพัฒนาท้องถิ่น/ตั้งงบประมาณประจำปี”
2. “อยู่นอกเหนืออำนาจงบประมาณของเทศบาล ให้ยุติใบงานและทำหนังสือประสานหน่วยงานเจ้าของพื้นที่ (กฟภ./กปภ./กรมทางหลวง)”
3. “ไม่คุ้มค่าทางวิศวกรรม ให้ยุติการใช้งบประมาณพิเศษและให้กองช่างซ่อมแซมบรรเทาความเดือดร้อนชั่วคราวตามวัสดุคงคลัง”

กำกับว่าเป็นเหตุผลตัวอย่าง ต้องตรวจทานข้อเท็จจริง อำนาจหน้าที่และแนวทางต่อก่อนยืนยัน ไม่รับรองว่าเป็นข้อกฎหมายที่ใช้ได้ทุกกรณี หน้ายืนยันต้องบอกว่าคำร้องนี้สิ้นสุดใน TownTrack และการเข้าแผน/หนังสือภายนอกเป็นแนวทางที่ผู้รับผิดชอบต้องดำเนินการต่อเอง การกดปุ่มไม่สร้างแผนงบประมาณหรือส่งงานภายนอกอัตโนมัติ

ใช้ API action DENY ที่ระบบมีจริง พร้อม version/idempotency/reason เดิม ไม่เพิ่ม endpoint /api/approvals/{id}/decision ตามชื่อสมมติในข้อความแนบ

TERMINATED แสดง “ยุติเรื่องตามผลพิจารณา” พร้อมคำอธิบาย “ยุติใบงานซ่อมด่วนตามผลพิจารณางบประมาณ (ดูเหตุผลและแนวทางดำเนินการต่อในรายละเอียด)” ใน tracking/detail และ staff dashboard เรื่องยังเป็น terminal ตาม backend เหตุผลสุดท้ายที่ประชาชนเห็นใช้ projection เดิม ไม่เปิดเผยบันทึกภายในเพิ่ม

## 5. เจ้าหน้าที่ส่วนกลางและการปิดทะเบียน

OFFICER display label: “เจ้าหน้าที่ส่วนกลาง (สำนักปลัด/ศูนย์รับเรื่องราวร้องทุกข์)” ทุกจุดที่เป็น label ของ role โดยคง key เดิม

เมื่อ RESOURCE_CHECK:
- หัวข้อ/คำอธิบาย: “ตรวจสอบความครบถ้วนทางสารบรรณและเลขที่เอกสารอ้างอิง (ก่อนเสนอผู้มีอำนาจพิจารณา)”
- SEND_APPROVAL: “เอกสารครบถ้วนตามระเบียบสารบรรณ - ส่งต่อผู้มีอำนาจ”
- ไม่เพิ่มการรับรองความถูกต้องทางการเงินหรืออำนาจกองคลังให้ OFFICER

เมื่อ OFFICER_REVIEW / RESOLVED แสดงว่ารายงานผ่านหัวหน้าผู้ลงพื้นที่มาก่อน และหัวข้อ:
“ตรวจสอบความสมบูรณ์ของภาพถ่าย Before/After เพื่อเผยแพร่ประชาสัมพันธ์และปิดทะเบียนคุมเรื่องร้องเรียน”
RETURN_LEADER ใช้ “ส่งกลับให้แก้ไข” และ label เหตุผล:
“ระบุสิ่งที่ต้องปรับปรุงเพิ่มเติม (เช่น ภาพถ่ายไม่ชัดเจนสำหรับแจ้งประชาชน หรือข้อมูลสรุปไม่ครบถ้วน)”
การให้เหตุผลปิดเรื่อง/ส่งกลับและขั้นตอนสิทธิ์เดิมยังอยู่

## 6. ข้อมูลติดต่อประชาชน

เบอร์โทรยัง optional, editable, prefill เมื่อข้อมูลจากบัญชีมีให้โดยไม่เดาค่าจาก username ช่องอีเมลยัง prefill/readOnly ตามที่ทำไว้

เพิ่ม helper ใหม่ตามคำขอรอบนี้ โดยปรับถ้อยคำตัวตนที่ผู้ใช้ยืนยัน:
“ไม่บังคับกรอกสำหรับการแจ้งซ่อมสาธารณูปโภคทั่วไป ระบบอ้างอิงตัวตนผ่านบัญชี Gov Center (LINE หรืออีเมล) ทั้งนี้ หากเป็นเรื่องร้องเรียนเหตุเดือดร้อนรำคาญหรือข้อพิพาททางปกครอง โปรดระบุหมายเลขโทรศัพท์เพื่อให้เจ้าหน้าที่ติดต่อกลับ”
ไม่อ้างว่า LINE ID อย่างเดียวทำให้ระบบผ่าน PDPA และไม่เรียกเรื่องที่มีบัญชีผูกตัวตนว่าไม่สามารถระบุตัวผู้แจ้งได้ ข้อมูลติดต่อยังไม่เผยแพร่ต่อประชาชนอื่นตามระบบเดิม

## 7. Gov auth badge และ UAT Fail-Closed

หลังยืนยันตัวตนสำเร็จ แสดง badge อ้างถึง Gov Center และ Central Gov Auth RBAC พร้อมคำอธิบายว่าสิทธิ์ใน TownTrack อาจปรับโดยผู้ดูแลตามระบบที่มีอยู่ ห้ามยืนยันว่ามีการตรวจสิทธิ์จาก Gov ทุกครั้งที่เปิดการ์ด เพราะ backend ปัจจุบันไม่ได้ทำเช่นนั้น หน้าล็อกอินใช้ป้ายแหล่งยืนยันตัวตน ไม่แสดงผลตรวจสำเร็จก่อนล็อกอิน

UAT build flag VITE_ENABLE_UAT_TOOLS ค่า default false เปิด true เฉพาะ cloud-test workflow ของเว็บทดสอบนี้ ไม่เปลี่ยนการตรวจสิทธิ์ backend หรือ production build ปกติ ไม่มี toggle นี้ใน production build ที่ไม่ได้เปิด flag

โหมด UAT แสดง toolbar ขนาดเล็กพร้อมป้าย “จำลอง / UAT” ที่หน้าล็อกอินและส่วนหัวภายใน ห้ามให้ UI จำลองเพิ่ม role หรือสร้าง session ปลอม
ชื่อสวิตช์: “จำลองสถานะ Gov กลางขัดข้อง (Test Fail-Closed 503)”
เมื่อเปิด แสดงข้อความตามคำขอ:
“ไม่สามารถเชื่อมต่อระบบยืนยันตัวตนส่วนกลางได้ เพื่อความปลอดภัยระบบจึงระงับการทำงานชั่วคราว (503 Service Unavailable - Fail-Closed)”
มีปุ่มคืนการเชื่อมต่อปกติ และกำกับว่าเป็นการจำลองฝั่ง UI ไม่ใช่หลักฐานว่า HTTP response ของ Gov เปลี่ยนเป็น 503 จริง

การจำลองต้องระงับ UI ภายในและคำขอธุรกิจใหม่ฝั่ง client โดยคงฟอร์มที่เปิดอยู่ mounted/hidden/inert เพื่อคืนร่างเมื่อปิดสวิตช์ ปิดการเปิดสวิตช์ขณะมี mutation/upload ที่กำลังทำงาน เพื่อไม่ทิ้งผลการบันทึกที่ยังไม่ทราบ ห้ามยกเลิก mutation ที่ส่งถึง server แล้วโดยสมมติว่ายังไม่ได้บันทึก เคลียร์โหมดจำลองเมื่อออกจากบัญชี ไม่ปิดหน้าประชาชนที่เข้าใช้งานอยู่

ถ้าการยืนยันตัวตนจริงตอบ 503 ให้แสดงข้อผิดพลาดที่ตรงกับ auth endpoint และไม่มีทางผ่านเข้า UI ภายใน ไม่เหมารวม 503 ของไฟล์/แผนที่เป็น Gov outage การจำลองนี้ไม่ถูกนำไปใช้แทนการทดสอบ server authorization จริง

## Responsive และ acceptance

ตรวจ 390 / 768 / 1280 px ในทั้งสองภาษา ปุ่มยาวและ badge ยาวต้องตัดบรรทัดได้ ไม่มี horizontal overflow, modal/footer ไม่ทับ input, keyboard focus/label ครบ แผนที่ไม่ล้นกรอบ

ทดสอบสำคัญ:
- สลับ TH/EN ระหว่างกรอกคำร้องพร้อมไฟล์/pin, ระหว่างกรอกรายการทรัพยากร, เหตุผลไม่อนุมัติ, และรายงานพร้อมไฟล์ร่าง ค่าทุกอย่างอยู่ครบ request payload และ role/state keys เดิม
- จำภาษาหลัง reload; storage error ไม่ทำให้หน้าใช้ไม่ได้; ข้อมูลผู้ใช้ไม่ถูกแปล
- รับงาน/เริ่มงานไม่ถามเหตุผล; ปฏิเสธและ DENY ยังบังคับเหตุผล; preset กรอกแล้วแก้ได้
- การ์ด FIELD แสดงวันจริง/โหวต 0/หมุดเดียว; error ไม่กลายเป็นข้อมูลว่าง; ไม่มี route planning/OSRM
- ป้ายพักทรัพยากรไม่ปรากฏหลังอนุมัติ; ชื่อคิวต่างภาษาไม่เปลี่ยน queue key
- เปิด/คืน UAT ระหว่างมีร่างโดยไม่สูญเสีย; ไม่มี mutation ใหม่ขณะจำลอง; ปุ่มจำลองไม่มีเมื่อ flag=false; 401/403/503 จริงไม่เปิดสิทธิ์
- regression ของ auth, privacy, 100m duplicate detection, emergency 199, PDF/media uploads และ municipal workflow
- ตรวจ git diff ว่าไม่มี backend/schema/API/workflow change ก่อน PR; ใช้ข้อมูลจำลองหรือฐานข้อมูลแยกเท่านั้น
